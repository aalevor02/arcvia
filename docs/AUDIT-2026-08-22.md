## 4. The plan editor silently loses the architect's work — four distinct ways
Merged: four findings, one component, one fix session. All in `apps/studio/src/screens/PlanEditor.tsx`. `updateScene(...{plan})` has exactly one call site (`:326`) and there is no local draft anywhere in `apps/studio/src`, so anything not PATCHed is gone.

**4a — In-flight edit dropped, UI says "Saved" (`:317-335`).** `save` is a dep of the effect whose cleanup cancels the pending write, so the request's own completion (`setSave('saved')`) tears down the timer armed for the edit made *while it was in flight*. Reproduced in real Chromium under the repo's React 18: label "Saved", `beforeunload` disarmed, server holds P1, wall B never sent. *Note: the original report's "slow connection widens the window" is backwards — when RTT exceeds the 1500 ms debounce the edit IS sent. The drop happens when the response lands before the newer edit's debounce expires, i.e. on a FAST connection.*
**Fix:** capture what was sent and re-dirty if the plan moved underneath:
```js
const sent = plan
await updateScene(scene.id, { plan: sent })
setSave(() => (planRef.current === sent ? 'saved' : 'dirty'))
```

**4b — "← Projects" inside the debounce discards the edit (`:476`, cleanup at `:334`).** `onBack` unmounts the component; React runs `clearTimeout(timer)`; no flush, no confirm, and `beforeunload` does not fire for `pushState` navigation.
**Fix:** keep the pending `{sceneId, plan}` in a ref whenever `save === 'dirty'`, and add one unmount-only effect (`useEffect(() => () => { if (pending.current) void updateScene(...) }, [])`). Do **not** flush from the autosave effect's cleanup — that fires on every keystroke.

**4c — After a save failure the unload guard disarms (`:339-344`).** The guard admits only `'dirty'` and `'saving'`. `'error'` — the one state where unsaved work definitely exists — removes the listener, and `:318` (`if (save !== 'dirty' …) return`) means nothing ever retries. There is no manual Save control.
**Fix:** `if (save === 'saved' || save === 'idle') return` in the unload guard, and allow `'error'` to re-arm the autosave timer with a longer delay.

**4d — A slow `getScene` overwrites what the user already drew (`:167-172`).** The canvas is interactive before the fetch is even issued (callback ref runs first) and the wall tool is pre-armed (`:117`, `!start` is true from the dashboard). The only guard is `cancelled`. `setHistory(initialHistory(...))` replaces `past` too, so the strokes are not recoverable by undo, and `save` is still `'dirty'` so autosave writes the server's own plan back and shows "Saved". Reproduced live: user's 2 walls gone, undo disabled, no error.
**Fix:** do not mount an interactive `PlanCanvas` before the scene resolves — render a loading state while `scene === null`. That is smaller and more correct than trying to merge two plans.

## 6. Every Cycles still is aimed at nothing — camera orientation is never axis-converted, and the lens is dropped
Merged: two findings, one seam (`services/api/src/routes/render.js:262-269`).
**Broken:** `position: toBlenderVec(cameraPosition)` applies Rx(+90°); `rotation: cameraRotation ?? null` forwards a Three.js **Y-up** world quaternion untouched, and `render-worker/render.py:270-279` applies it directly to a camera in a Z-up scene (glTF import has already rotated the model). Separately, `SceneViewer.ts:1026` emits `focalLength`, `render.py:257` reads `camera_spec.get("focalLength", 35.0)` — and `apps/studio/src/lib/renderClient.ts:68-77` never sends it, so the worker silently falls back to 35 mm.
**Consequence:** Measured — a camera at (6,4,6) framing the origin renders aimed at (0,−10,−2): **65.9° off**. A level walkthrough camera (identity quaternion) points straight at the floor, 90° off and rolled 90°. On top of that, the 16:9 presets render at hFOV 54° instead of the composed 79° — a 1.6× tighter crop. The user pays 1–5 credits per still and gets sky or ground. `docs/handover.md:106` claims the conversion "happens in exactly one place"; the orientation half was never written anywhere. The one test that touches this, `services/api/test/bake.mjs:190-192`, asserts the position only — which is why CI is green.
**Fix:** premultiply the quaternion by the same Rx(+90°) the position gets:
```js
const Y2Z = { x: Math.SQRT1_2, y: 0, z: 0, w: Math.SQRT1_2 }
rotation: cameraRotation ? quatMul(Y2Z, cameraRotation) : null,
```
and extend `bake.mjs:190` to assert the resulting aim vector, not just the position.
For the lens, do **not** just forward `focalLength` — Three fits filmGauge 35 to height while Blender's AUTO fit maps 36 mm to the larger dimension (~2% residual). Send `fovY` (`camera.fov`) and in `render.py:257` set `data.sensor_fit = 'VERTICAL'; data.sensor_height = 24.0; data.lens = 12.0 / tan(radians(fovY)/2)`. Exact at any aspect.

## 8. `RENDER_CONCURRENCY` is not enforced — one freed slot launches the whole backlog
**Broken:** `services/api/src/lib/renderQueue.js:124-135`. `while (running.size < CONCURRENCY …) { … void start(job) }`, but `start()` suspends at its first statement (`:140 await db.update(...)`, which does a real fs write) and every `running.set` is downstream of it (`:169`, `:189`, `:254`, `:291`). `running.size` is unchanged on the next iteration, so the loop shifts the entire `pending` array.
**Consequence:** Reproduced twice at `RENDER_CONCURRENCY=1`: 5 jobs POSTed to the stub GPU worker in a 9 ms window; and 5 simultaneous Blender children in the default local mode. In remote mode that is 5× the operator's configured worst-case burn — the exact number `renderQueue.js:34-37` calls "the single most important number for cost control". In local mode it is N Cycles bakes contending for the same CPU (measured elsewhere in this repo at ~2× wall-clock for a second job, `docs/PENDING-ARCVIA.md:543`), several of which then cross `BAKE_TIMEOUT_MS` and are SIGTERM'd → the user submits four renders and gets four timeouts. `docs/engine-blueprint.md:1016` assumes concurrency 1 actually serialises; it does not.
**Fix:** reserve the slot in `drain()` before yielding:
```js
const job = pending.shift()
running.set(job.id, { child: null, startedAt: Date.now(), progress: 0, markers: {} })
void start(job)
```
and change the four `running.set` calls inside `start()` to `Object.assign(running.get(job.id), {...})`. `finish()` already deletes the entry on every exit path.
*Correction to the report: the "two submissions milliseconds apart both start" sub-claim did not reproduce — the awaited `db.insert` in the submit route lets the first job register. The backlog case is the real one, and it is guaranteed by construction.*

**Broken:** `apps/studio/src/catalogue/build.ts:29-43` — `TONE_SURFACE` has ten keys and `material(tone) => surface(TONE_SURFACE[tone] ?? 'fabric')`. The pool builder at `:345-349` passes `'floor-tile'`, a real `SurfaceKind` (`materials.ts:389`) that is not a `TONE_SURFACE` key. It is the only tone literal in the file that misses.
**Consequence:** Ran the shipped `buildObject`: the tank floor and all four tank walls come back as the *same material instance* as `surface('fabric')`. `upgradeSurfaces` then mutates that shared instance in place with ambientCG **Fabric030 grey woven upholstery** (`surfaces.ts:119-130`). Water is deliberately `opacity: 0.72` "so the pool floor shows through", and a ~170 mm band of tank wall is visible above the waterline around the whole perimeter, so it is seen two ways. Neither TypeScript nor the existing `surfaces.test.ts` can catch it — `block(group, tone: string, …)` and `Record<string, SurfaceKind>` both accept any string.
**Fix:** add `'floor-tile': 'floor-tile'` to `TONE_SURFACE`, and add a test that every tone literal passed to `block()`/`cylinder()` in `build.ts` is a key of `TONE_SURFACE`. Otherwise the next tone added to a builder does this again silently.

## 19. `RENDER_MODE=remote` never releases a finished job
**Broken:** `renderQueue.js:254` — `running.set(job.id, {...})` with the comment "The worker owns the job now and will call back when it finishes". The callback (`render.js:359-381`) only writes the DB; `render.js:5` imports `{ enqueue, jobStatus, cancelJob, queueDepth }`, so there is no exported way to complete a job. `running.delete` exists only in `cancelJob` (`:114`) and in `finish` (`:145`), which is unreachable on a successful remote dispatch. `render.js:311-314` then prefers the stale in-memory value (`live?.status ?? job.status`).
**Consequence (when someone builds a worker):** the DB says `done` with an `outputUrl` and `GET /render/jobs/:id` says `rendering`; `renderClient.ts:126-128` polls to the 15-minute timeout and throws "The render is taking unusually long" — a paid, completed render never reaches the customer. With `CONCURRENCY=1`, exactly one remote render ever runs per process lifetime. `completedToday` lives in `finish()`, so `RENDER_DAILY_CAP` is permanently 0 in the only mode that costs GPU money. No timeout timer is armed either (the `setTimeout` at `:283` is below the remote `return`), so a worker that dies never fails the job.
**Ranked here, not at the top, because no worker ships in this repo** — `services/render-worker` holds only Blender Python, and `.env` runs `RENDER_MODE=local`. This is a pre-flight blocker for the day you write the worker, not a live customer bug. Fix it *before* that day, since it wedges on the first job.
**Fix:** export `completeJob(jobId, status, patch)` from `renderQueue.js` that runs the same body as `finish()` (delete from `running`, increment `completedToday`, update the row, settle the refund, `drain()`), and call it from `render.js:369` instead of `db.update`. Arm a `JOB_TIMEOUT_MS` timer on the remote branch too.

## 20. `put()` skips the write whenever the path merely exists — a torn write poisons a content-addressed key forever
**Broken:** `services/api/src/lib/storage.js:96-104`. The comment says "the identical bytes are already there"; the code checks existence. `stat` succeeds for a half-written file, `writeFile` at `:101` is not atomic, and `:104` returns `bytes: buffer.length` regardless.
**Consequence:** Measured a ~60–130 ms exposure window per 64 MB upload (Node writes in chunks; `server.js:55` permits 4 × 64 MB per request), and SIGKILL during it — docker stop timeout, OOM kill, host reboot — leaves a partial file. ENOSPC does the same with no kill at all. After that, every re-upload of the same drawing hashes to the same key, `stat` succeeds, the write is skipped, and the route answers 201 with the full byte count. `uploads.js:143-163` then serves the truncated bytes with `Cache-Control: immutable` under a comment asserting "the bytes behind a URL can never change". The architect re-uploads to fix a drawing the engine choked on, is told it uploaded, and gets the identical failure with no product surface able to delete the file. *Note: a client-side truncation is harmless — short bytes hash to a different key. Only a torn disk write poisons.*
**Fix:** `const info = await stat(path); if (info.size !== buffer.length) throw new Error('resize')` inside the try so the catch rewrites; and write to `path + '.tmp'` then `rename`, the same pattern `store.js` now uses.

## 21. Every render leaves a full-size duplicate of its output on the worker's disk, forever
**Broken:** `renderQueue.js:419-433` — `publish()` reads `outputPath`, copies the bytes into content-addressed storage, and never unlinks the original. The CAD path (`:220-221`) publishes out of `job.spec.outDir` and never removes it either. No cron, TTL, sweeper or maintenance route exists.
**Consequence:** In this repo right now: `.data/renders` = 15 MB of byte-identical orphans from five jobs (sha256 prefixes match the uploads filenames exactly), and `.data/cad` = 134 MB. Unbounded growth until Blender can no longer write, at which point every render fails.
*Two corrections — the report inflated this.* `ARCVIA_OUT_DIR` is **not** unset in production (`.env.example:34`, `docs/handover.md:160`), so the "/tmp is tmpfs, i.e. RAM" escalation is invented. And "500 jobs/day = 1–3 GB/day" is unreachable at `CONCURRENCY=1` with a 45-minute bake timeout — realistic worst case is ~100–190 MB/day. The `render.py:57 delete=False` sub-claim is unreachable in local mode, since `resolveUrl` never yields an http URL.
**Fix:** `await unlink(outputPath).catch(() => {})` after the `put()` in `publish()`, and `await rm(job.spec.outDir, { recursive: true, force: true })` after the CAD publish — but keep the resume-cache semantics of `render_views.py:20-25` in mind for the multi-frame path.

## 22. `phoneVerified` stays true after the number is changed
**Broken:** `services/api/src/routes/auth.js:313` writes the new phone without clearing the flag; `:329` then short-circuits `/otp/verify` on the stale flag before the code is compared.
**Consequence:** Verified live — verify your own number, POST `/otp/send` with a stranger's number, POST `/otp/verify` with `000000` → `{verified:true, alreadyVerified:true}`, and `/auth/me` reports the new number as verified. An SMS is paid for and delivered to a number that never consented. **But nothing in the product reads `phoneVerified` today** (grep hits only `auth.js` and `organisation.js:84`, which initialises it to `false`), so the current damage is a wasted SMS and a wrong database field. It becomes real the day anything trusts it.
**Fix:** `await db.update('users', user.id, { phone, otp, phoneVerified: phone === user.phone && user.phoneVerified })` at `:313`. One line.
